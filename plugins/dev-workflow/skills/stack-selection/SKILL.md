# スタック選定

新しいアプリや大きな機能の最初に、使うライブラリ・フレームワーク・スキルを調べて提案し、決めた理由を残す。

## 既定の方針(ユーザーが別の指示をしたらそちらに従う)

- **ライブラリは積極的に使う。** 自作より、広く使われて保守されているライブラリを選ぶ。UI の部品、地図、グラフ、状態管理、フォーム、日付、テストなど、層ごとに定番を当てる。
- **重い処理は事前に済ませる。** 前処理・集計・モデル学習はローカルのスクリプトで行い、結果を静的ファイルとして配る。ブラウザでは軽い再計算だけにする。
- **使えるスキルも選定の対象にする。** ライブラリと同じ表で「どの作業にどのスキルを使うか」を提案する。

## 手順

### 1. 要件を短く整理する

次を3〜8行で書き出す。分からない項目は、推奨の答えを添えて1回にまとめて質問する(`grilling` スキルがあればそれを使う)。

- 何を見せ、何を操作させるか(画面と主な操作)
- データの種類・件数・更新頻度・出典
- 配信先(静的ホスティング、サーバーの有無)と費用・認証の制約
- 利用者の端末(PC/スマホ)、言語、アクセシビリティ
- 期限(何時間・何日で動くものが要るか)

### 2. 使えるスキルを棚卸しする

- いま読み込まれているスキル一覧、プロジェクトの `.claude/skills/`、導入済みプラグインを確認する。
- 作業ごとに使えるものを対応づける(例: 画面の見た目 → デザイン系、グラフ → 可視化系、デプロイ → ホスティング先のスキル、仕様の詰め → 質問系、根拠の文書化 → `doc-driven`)。
- 足りない作業があれば「スキルなし」と書く。無理に当てはめない。

### 3. 候補を調べる(記憶で決めない)

層ごとに2〜3候補を挙げ、**いまの状態を確かめてから**比べる。

| 層の例 | 見るもの |
|---|---|
| ビルド・フレームワーク | 静的出力できるか、配信先との相性 |
| UI の部品 | アクセシビリティ、見た目の自由度、日本語(フォント・IME) |
| 地図・グラフ | 描画件数の上限、スマホでの速さ、凡例・ツールチップ |
| 状態管理・URL 共有 | 学習コスト、URL との同期 |
| テスト | 単体・画面のテストのしやすさ |
| 前処理 | 入力形式(CSV/GeoJSON/Shapefile 等)への対応、再現性 |

確かめ方:

- 最新版と更新日: `npm view <pkg> version time.modified`、`uv pip index versions <pkg>`、公式のリリースノート。
- **組み合わせの相性**: peer dependency と主要バージョンの対応表を公式文書で確かめる(地図×オーバーレイ、UI×React など、ここで詰まりやすい)。
- ライセンス、配布サイズ、保守の活発さ(最近のリリース・未解決 issue の量)。

### 4. 提案する

- 層ごとに **推奨を1つ** と理由を1行。代替は、本当にトレードオフがある場合だけ書く。
- 使うスキルの対応表を付ける。
- 見送った候補と見送った理由を短く書く。
- 決めるのはユーザー。承認を待ってから導入する。

### 5. 一番危ない組み合わせを先に試す

承認後、相性が最も不安な組み合わせを最小構成で入れて、ビルドと表示まで通す(`npm ls` で依存の警告も見る)。ここで詰まったら提案を直す。

### 6. 決定を残す

- `doc-driven` を使っているプロジェクトなら `docs/decisions/<名前>.md` に、そうでなければ README か ADR に書く。
- 書くこと: 採用したもの(バージョン付き)、理由、見送ったもの、前提(配信先・事前計算の範囲)、見直す条件。

## してはいけないこと

- 記憶にあるバージョンや API をそのまま前提にすること。必ず確かめる。
- 承認前に大量の依存を入れること。
- 要件にない機能のためにライブラリを足すこと(「多用」は、要件のある層を自作しないという意味)。
