# PDCA

変更を小さな Plan → Do → Check → Act の輪で進める。一番大事なのは **Check を自分から行うこと**。ユーザーの質問で誤りが見つかる状態は、Check が足りていない合図。

## Plan(作る前に書く)

変更ごとに、次を数行で決めてから手を動かす(`doc-driven` を使っていれば `SPEC.md` や `docs/` に、そうでなければ作業メモに)。

- **目的**: 何のための変更か。
- **期待する結果**: できれば数字で(件数、合計、範囲、表示されるもの)。「人口合計は公式値の±1%」「新しい候補は町の全域に出る」など。
- **確かめ方**: どの独立した根拠と比べるか(公式統計、元データの件数、実際の画面、定義書)。
- **やらないこと**: 今回の輪に入れないもの。

形式が選べる成果物(図、画面、文書の体裁)は、作る前に形式をユーザーに一言確かめる。

## Do(小さく作る)

- 1つの輪は、1つのコミットで説明できる大きさにする。
- 決め打ちの値(範囲、件数、ファイル名)を置くときは、どこから来た値かをコードに残す。可能なら入力から計算する。

## Check(自分で確かめる)

当てはまるものを全部行い、**何を確かめて何を確かめていないか**を記録する。

### データ

- **合計を公式の値と突き合わせる。** 自治体の人口、元データの総件数など、加工前の独立した数字と比べる。差があれば原因が分かるまで先に進まない。
- **端と境界を見る。** 範囲の端(地図なら対象地域の四隅)、行政界をまたぐ単位、欠損・0・重複。
- **元データの定義を読む。** 値が無い・0 の意味、含まれないもの、集計単位の決め方を、提供元の資料で確かめる。

### 計算

- 期待値のテストを置く(主要な合計・件数・代表ケース)。
- 極端な入力(最小・最大の設定、空の結果)でも動くか。

### 画面

- 実際に開いて見る(スクリーンショットを撮る)。PC 幅とスマホ幅の両方。
- コンソールのエラー、読み込みの失敗、表示されないレイヤー。
- 画面の説明文・凡例・注意書きが、データの定義と合っているか。

### 説明

- ユーザーへの報告や文書の説明が、確かめた事実と一致しているか。推測は推測と書く。

## Act(次につなげる)

- 分かった事実を文書に戻す(`doc-driven` なら `docs/` と `docs/log.md`)。
- 見つけた誤りは、**同じ種類の誤りを捕まえるテスト**にする(例: 合計値の照合をテストに入れる)。
- 次の手を決める: 続ける / 直す / やめる。残った限界と未確認の項目を一覧にする。
- ユーザーに報告するときは「確かめたこと」「確かめていないこと」「次にやること」を分けて書く。

## 振り返り(節目、またはユーザーが求めたとき)

1. 事実を集める: コミット履歴、`docs/log.md`、見つかった誤りと、それを見つけたきっかけ(自分の Check か、ユーザーの指摘か)。
2. **良かった点**: 続けたいやり方と、それが効いた具体的な場面。
3. **悪かった点**: 起きたこと・影響(数字で)・本来どこで気づけたか。言い訳や一般論にしない。
4. **次に活かすこと**: 次の輪の Plan や Check に入れる具体的な手順。繰り返し使えるものは、このスキルやプロジェクトの指示書(AGENTS.md / CLAUDE.md)に足すことを提案する。

## よくある失敗(これを防ぐための Check)

- 境界をまたぐ単位を捨てて、合計が1割以上減っていた → 合計の照合。
- 範囲を決め打ちにして、対象地域の端のデータが欠けていた → 端を見る、範囲を入力から計算する。
- データの「0」や「無い」を、定義を読まずに説明した → 定義を読む。
- 図の形式を確かめずに作り、何度も作り直した → Plan で形式を確かめる。
- 対象外のもの(他の交通手段など)を数えないまま数字を見せ、実態とかけ離れた結果になった → 限界を Plan に書き、画面に出す。
